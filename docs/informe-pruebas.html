Las 122 verificaciones ejecutadas pasaron. Además, la campaña detectó tres defectos reales que no estaban documentados en el proyecto y que se detallan en la sección 06: el límite de memoria efectivo es el doble del declarado, el techo de estudiantes concurrentes lo impone la red y no la RAM, y la destrucción de instancias desperdicia cinco segundos por contenedor.

Encontrar defectos no contradice los resultados: las pruebas se diseñaron para atacar el sistema, y un sistema que se deja medir es el que puede corregirse.

02

Metodología

La validación se organizó en cuatro niveles, de menor a mayor contacto con el entorno real. Los dos primeros responden «¿está bien construido?»; los dos últimos, «¿aguanta?».

Niveles de prueba
NivelQué compruebaEntornoCasos

Humo Ciclo de vida completo de una instancia contra el motor real Docker Engine real 10
Estrés Resistencia del aislamiento ante ataques desde dentro del contenedor Docker real · dos configuraciones 8

En las pruebas de estrés cada ataque se ejecuta dos veces: primero sobre un contenedor sin los límites del sistema y después sobre uno con la configuración real de la plataforma. Así la mejora queda medida, no afirmada — es el origen de los cuadros comparativos de este informe.

El dato que cierra el caso del techo de consolas

El host tiene 12 CPU, de modo que el pool de hilos de Python admite como máximo 16 — exactamente el techo histórico documentado en el proyecto. Si cada consola consumiera un hilo propio, 20 consolas serían imposibles: el pool se agotaría en la decimosexta.

Se midieron 20 consolas simultáneas funcionando, con cero hilos bloqueados en entrada/salida de socket, tanto durante el arranque como con todas las terminales abiertas en reposo. Los 17 hilos presentes están en futex_wait_queue: ociosos, esperando trabajo, no bloqueados.

07

Defectos encontrados

Tres defectos que las pruebas revelaron y que no estaban documentados en el proyecto. Ninguno compromete el aislamiento; los tres afectan la capacidad o el aprovechamiento de recursos.

Hallazgo 1 · severidad alta · capacidad

El techo de estudiantes lo impone la red, no la memoria

Al elevar la prueba de carga a 30 estudiantes, seis despliegues fallaron con error 500. La causa no es memoria ni CPU: Docker agota sus rangos de direcciones predefinidos alrededor de la red número 24.

$ docker network create --internal ctf-pool-test-24 Error response from daemon: all predefined address pools have been fully subnetted

La documentación del proyecto estima «50-60 contenedores simultáneos» a partir de la memoria. El límite real medido es de 24 a 31 estudiantes, porque cada uno consume una red completa. Corrección en /etc/docker/daemon.json:

{ "default-address-pools": [ { "base": "10.200.0.0/16", "size": 24 } ] }

Con máscara /24 sobre esa base se obtienen 256 redes, y el techo vuelve a depender de la memoria del host.

Hallazgo 2 · severidad media · recursos

El límite de memoria efectivo es el doble del declarado

La plataforma declara Memory pero no MemorySwap. Docker concede entonces una cantidad de swap igual al límite de RAM, así que cada contenedor puede llegar a 512 MB en lugar de los 256 MB documentados. Un contenedor con límite de 256 MB asignó 400 MB sin problema; declarando el tope de swap, el kernel lo detuvo con código 137.

# ctf/docker_client.py · HostConfig "Memory": mem_limit_bytes, + "MemorySwap": mem_limit_bytes, # sin esto, Docker concede otro tanto de swap
Hallazgo 3 · severidad media · rendimiento

Cada destrucción desperdicia cinco segundos

El proceso principal del contenedor es un shell que no termina al recibir SIGTERM, así que Docker espera el tiempo de gracia completo antes de forzar el cierre.
